# S3-1 职位导入与 JD 条件设计

日期：2026-10-14（Asia/Shanghai）。本阶段只提供用户私有职位、JD 规则整理和人工审核；匹配属于 S3-2。

## 数据与模块边界

`job_catalog` 负责职位、原文快照、来源、收藏、授权、幂等和版本；`job_intelligence` 负责可替换的 `JDParser` 接口及确定性规则实现。HTTP 路由只装配身份、CSRF 和 Schema，不访问招聘链接。前端使用后端 OpenAPI 生成的类型，沿用现有中文工作台。

职位基本信息包括名称、公司、城市、薪资原文、实习/校招/正式工作/未知、来源链接与粘贴或手工来源。仅名称必填，未知字段保留空值；薪资不擅自换算月薪，工作类型不根据职位名称推断。JD 最大 30,000 字符，每职位最多 100 条条件。

## 条件 Schema

每条条件保存类型、原文或用户修订内容、`must/preferred/uncertain` 分类、`pending/confirmed` 审核状态，以及来源快照版本、证据、零起始字符区间、行号、创建/修改/审核时间、条目 revision、Schema/解析版本。类型覆盖学历、专业、毕业届别、经验、地点/到岗、实习时长、技术、项目、实习经历、语言、职责、薪资、工作性质和其他条件。

原文证据在服务端按实际快照重新定位、校验，位置是 Python Unicode 字符索引，左闭右开；不是 UTF-8 字节偏移或浏览器 UTF-16 code unit。重复引文需提供明确起点，不能让服务器猜引用了哪一处。用户补充的条件允许无 JD 引文，但来源明确为用户提供，不制造证据。

## 确定性规则

规则按行与句/分号分句，保留逐字原文。明确任职要求、优先条件、岗位职责等标题只提供局部上下文；“优先/加分”不得升级为必须。混合措辞、范围不明确、否定、替代条件、可协商或需核实等保守进入待核实。规则不展开“相关专业”的范围、不推算毕业日期/经验年限，也不补未出现的技能。

规则没有模型、Prompt、工具执行或网络访问；JD 内的命令、HTML 和脚本仅为不可信文本。预览响应通过版本化 Schema，所有自动条件初始为 `pending`，输出数量达到上限会明确提示人工检查遗漏，原始 JD 不截断。界面明确显示“免费规则整理”，不包装成真实 AI 分析。

规则是可审核的词法首版，无法证明自然语言语义完整或招聘信息真实；复杂复合句可能需人工拆分、重分类或补充。接口可后续接入经单独授权、严格 Schema 验证的 Provider，本阶段不安装 Agent 框架或调用付费模型。

## 审核与版本

用户先粘贴 JD，填写或修正基本信息，再显式整理、逐条确认/修改/删除/补充、保存。可以只审核部分条件并保存进度；不能把一次保存当作全体确认。

中文页面修改已确认条件会撤销确认，用户再次核对后可确认；API也允许用户在同次修改请求中显式声明已审核。所有职位写入共用职位 `revision` 的条件更新，旧版本返回 409，前端保留输入并允许核对最新保存内容。创建用用户隔离的幂等键和内容校验；网络结果不明时不自动重复写。收藏也推进版本。

修改 JD 推进 `jd_version`，保存新的不可变原文快照，使旧来源条件的确认失效并显示需重新审核。旧条件及引文仍绑定旧快照；不能通过新 JD 的相似文本静默恢复确认。后续匹配必须检查条件确认状态与当前 JD 版本。

## 安全与生命周期

服务端从既有会话解析用户，读写均按 owner 查询，不接受客户端归属。未知与跨用户资源统一 404；所有写请求复用 CSRF/Origin 校验。招聘链接仅保存为公共 HTTP(S)，拒绝危险 Scheme、凭据、控制字符、非标准端口和明显私网地址，不执行 DNS/服务器抓取。页面用文本渲染 JD 与证据；新窗口来源链接带 `noopener noreferrer`。

新字段只服务于用户收藏和理解招聘岗位；不增加联系方式、学历或其他个人事实收集，不改变正式画像。JD、证据、链接与正文不进入日志、追踪和评测样本。删除职位清除其快照与条件；幂等记录只保留最小防重信息。未提供账户级导出/注销或自动保留期限，备份保留和删除重放沿用既有上线前待决事项，逻辑删除不代表磁盘安全擦除。

## S3-2 的输入门槛

匹配只读取 S2 的正式画像及当前版本经用户确认的职位条件；待审核、待核实、旧快照或缺少依据的条件应保持未知。需要独立确定性规则、版本化结果与画像/JD revision 失效机制，并覆盖明确满足、部分满足、未发现证据、明确不满足四态。不要将简历缺少描述推断为用户没有能力。本阶段不创建匹配表、评分、推荐或投递记录。
